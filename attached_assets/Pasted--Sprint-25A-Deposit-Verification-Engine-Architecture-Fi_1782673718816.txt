# Sprint 25A — Deposit Verification Engine (Architecture First)

## Objective

Build a complete Deposit Verification Engine for Prime Wave that automates BEP20 USDT deposit verification without using any third-party payment processor.

IMPORTANT:

This sprint is NOT about integrating Binance Smart Chain yet.

This sprint builds the platform, workflow, state machine, APIs, database, admin tools, background processing and UI.

The actual blockchain integration will come in Sprint 25B.

────────────────────────────────────────
NON-NEGOTIABLE ARCHITECTURE
────────────────────────────────────────

The Deposit Verification Engine must NEVER contain blockchain-specific code.

Instead implement this layered architecture:

Deposit Page
        │
        ▼
Deposit Verification Engine
        │
        ▼
Blockchain Adapter Interface
        │
        ▼
Mock Blockchain Adapter (Sprint 25A)

Later we will simply replace:

MockBlockchainAdapter

with

BSCBlockchainAdapter

without modifying the Deposit Engine.

The Deposit Engine must communicate ONLY through the Blockchain Adapter interface.

BUSINESS FLOW
────────────────────────────────────────

User opens Deposit page.

System displays:

• Prime Wave BEP20 USDT wallet address
• QR Code
• Network = BEP20

• verifyTransaction(txHash)

• validateToken(...)

The Deposit Engine must know nothing about BSC implementation.

────────────────────────────────────────
MOCK BLOCKCHAIN ADAPTER
────────────────────────────────────────

Create a deterministic mock adapter.

It must simulate:

✓ Valid transaction

✓ Pending confirmations

✓ Invalid hash

✓ Wrong network

✓ Wrong recipient

✓ Wrong token contract

✓ Duplicate transaction

✓ Failed blockchain transaction

This allows complete end-to-end testing before connecting to the real blockchain.

────────────────────────────────────────
WALLET RULES
────────────────────────────────────────

The blockchain is the source of truth.

Never trust:

• user-entered amount
• user-entered network
• user-entered recipient

Wallet credit must always use the blockchain adapter response.

Reuse the existing deposit approval and wallet credit pipeline wherever possible.

Do NOT create parallel wallet credit logic.

────────────────────────────────────────
IDEMPOTENCY
────────────────────────────────────────

Transaction Hash must be globally unique.

The same blockchain transaction can NEVER credit twice.

Protect against duplicates at:

1. Database level
2. Service level

────────────────────────────────────────
BACKGROUND WORKER
────────────────────────────────────────

Never keep HTTP requests open while waiting for confirmations.

Flow:

Submit TX

↓

Return

"Verification Started"

↓

Worker polls adapter

↓

Updates status

↓

Credits wallet

↓

Stops

Everything asynchronous.

────────────────────────────────────────
CRITICAL ARCHITECTURE RULE
────────────────────────────────────────

The Deposit Verification Engine is an orchestration layer only.

It must NOT:

• hardcode blockchain logic
• hardcode BEP20 rules
• directly call RPC nodes

It must ONLY communicate through the Blockchain Adapter interface.

If existing services already perform deposit approval, wallet crediting, ledger creation, notifications or audit logging, REUSE those services instead of duplicating logic.

The Deposit Verification Engine should orchestrate the existing financial architecture rather than replacing it.
