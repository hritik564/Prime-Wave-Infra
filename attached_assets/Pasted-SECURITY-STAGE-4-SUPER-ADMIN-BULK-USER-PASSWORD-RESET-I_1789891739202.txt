SECURITY STAGE 4 — SUPER ADMIN BULK USER PASSWORD RESET
IMPLEMENTATION ONLY — DO NOT EXECUTE THE MASS RESET

We have completed Stage 1 and Stage 2 of the user credential-reset infrastructure.

IMPORTANT CHANGE IN REQUIREMENTS:

We do NOT want the mass reset to depend on email/SMS delivery.

The company will distribute the newly generated credentials manually.

The objective is to build a secure Super Admin-only backend operation that can generate a UNIQUE new password for every normal user and replace their existing password hash in bulk.

DO NOT execute the mass reset in this task.

DO NOT modify existing production user passwords.

DO NOT increment authVersion for the production user population.

DO NOT set passwordResetRequired=true for the production user population.

DO NOT deploy the mass-reset operation.

This task is implementation + testing only.

==================================================
1. SCOPE
==================================================

The operation must target ONLY the normal User model/table.

Target population:

- ACTIVE users
- INACTIVE users
- BLOCKED users, if they exist
- SUSPENDED users, if they exist

All normal users should be included unless an explicit exclusion is configured.

Current expected population is approximately 6,640 users.

IMPORTANT:

Admins use a separate Admin model/table.

NEVER include:

- SUPER_ADMIN
- FINANCE_ADMIN
- SUPPORT_ADMIN
- REWARD_MANAGER
- STAFF_OPERATIONS

Admin accounts must be completely excluded from the bulk operation.

Do not infer admin status from email addresses.

Use the separate Admin model and User model boundaries.

==================================================
2. SUPER ADMIN AUTHORIZATION
==================================================

Create a dedicated bulk-reset operation available ONLY to:

SUPER_ADMIN

Reject:

- STAFF_OPERATIONS
- SUPPORT_ADMIN
- FINANCE_ADMIN
- normal users
- unauthenticated requests

Use the existing secure Admin authentication/authorization middleware.

Do not create a new authentication mechanism.

==================================================
3. BULK RESET DESIGN
==================================================

For every selected normal User:

1. Generate a cryptographically secure random password.

Use Node's cryptographic randomness facilities such as randomBytes/randomInt.

DO NOT use:

Math.random()

DO NOT derive passwords from:

- user ID
- username
- email
- phone
- sequential numbers
- company names
- dates

Every user must receive a different password.

2. Hash the generated password with the application's existing bcrypt configuration.

3. Replace users.passwordHash.

4. Set:

passwordResetRequired = true

5. Increment:

authVersion

6. Update:

passwordChangedAt

7. Preserve ALL other User fields.

==================================================
4. FINANCIAL DATA SAFETY
==================================================

The bulk reset must modify ONLY authentication-related fields:

- passwordHash
- passwordResetRequired
- authVersion
- passwordChangedAt

It MUST NOT modify:

- wallet balances
- locked withdrawal balances
- wallet addresses
- wallet transactions
- investments
- ROI ledger
- deposits
- deposit verification
- withdrawals
- withdrawal locks
- income
- binary income
- level income
- salary income
- BV ledgers
- referral relationships
- sponsor relationships
- binary tree relationships
- KYC/profile data
- account status
- usernames
- emails
- phone numbers

Use an explicit update projection.

Do not use a broad object replacement/update that could overwrite unrelated User fields.

==================================================
5. EXISTING AUTH VERSION
==================================================

The production population currently uses authVersion=0 unless the preflight discovers otherwise.

Do NOT assume this blindly.

The operation must:

authVersion = authVersion + 1

rather than setting it to a hard-coded value.

This guarantees that every existing JWT becomes stale.

After the reset:

- old JWTs must fail
- new login with the generated password must work
- passwordResetRequired must be enforced

==================================================
6. PASSWORD RESET REQUIRED
==================================================

After the bulk reset:

passwordResetRequired=true

The existing authentication middleware should prevent normal authenticated access until the user establishes a new permanent password.

Do not bypass the existing Stage 1/2 reset enforcement.

The bulk operation itself does NOT need to send reset emails.

The company will distribute the generated temporary credentials manually.

==================================================
7. CREDENTIAL EXPORT
==================================================

We need a secure way for the Super Admin to receive the generated credentials.

DO NOT:

- print passwords to console logs
- store plaintext passwords in the database
- store plaintext passwords in application logs
- store plaintext passwords in Redis/cache
- expose passwords through ordinary API responses
- include passwords in audit logs
- include passwords in analytics
- include passwords in error messages

Instead implement a controlled one-time credential export.

Preferred design:

Generate a temporary credential artifact containing:

- user ID
- username
- email
- generated temporary password

ONLY for users included in the reset.

The artifact must be created outside the database.

It must NOT be placed in a public/static web directory.

It must NOT be committed to Git.

It must NOT be uploaded automatically to GitHub.

It must NOT be written into application logs.

The artifact should have a clearly defined lifecycle and should be removable after successful distribution.

If the current application architecture has a safer existing secure-download mechanism, use that instead.

IMPORTANT:

The raw password may exist temporarily in application memory during generation/export, but MUST NOT persist after the credential artifact lifecycle is complete.

==================================================
8. DO NOT CREATE A PERMANENT CREDENTIAL TABLE
==================================================

Do NOT create a database table containing plaintext temporary passwords.

Do NOT store temporary passwords in:

- users
- password_reset_tokens
- audit tables
- notifications
- system_settings

Only the bcrypt hash belongs in the User record.

Before an actual execution endpoint/action exists, implement a safe preflight/preview operation.

It should report:

- users excluded
- whether any unexpected authVersion values exist

The preview MUST NOT modify data.

Example conceptual endpoint:

SUPER_ADMIN only.

No password generation is necessary during preview.

==================================================
10. EXECUTION SAFETY
==================================================

Create a separate explicit execution endpoint/action.

Example:

POST /api/admin/security/bulk-password-reset/execute

SUPER_ADMIN only.

It must require an explicit confirmation payload such as:

{
  "confirmation": "RESET ALL NORMAL USER PASSWORDS",
  "expectedUserCount": <count>
}

Reject execution if:

- confirmation is incorrect
- expectedUserCount does not match the current eligible count
- admin count unexpectedly changes
- user count unexpectedly changes
- any safety precondition fails

Do NOT allow a generic boolean such as:

confirm=true

to be sufficient.

The confirmation phrase should be exact.

==================================================
11. BATCHING
==================================================

Do NOT attempt to update 6,640 users through one enormous transaction if that creates unnecessary database risk.

Use controlled batches.

For example:

100–500 users per batch.

The exact batch size should be selected based on the existing PostgreSQL/Prisma architecture.

Each user update must be atomic.

If a batch fails:

- stop the operation
- report which batch failed
- do not silently continue
- do not generate duplicate credentials for already completed users

The operation must have a clear checkpoint/progress mechanism.

==================================================
12. IDEMPOTENCY / RESUME SAFETY
==================================================

This is extremely important.

Do NOT make the operation blindly repeatable.

A second execution must NOT generate another password for users who have already been reset unless explicitly intended.

Implement a safe execution identity/run ID.

Track:

- run ID
- startedAt
- completedAt
- total eligible users
- users processed
- users remaining
- failure state

Do NOT store plaintext passwords in this run record.

If a run stops halfway, it must be possible to identify exactly which users were successfully processed without exposing their passwords.

==================================================
13. CREDENTIAL ARTIFACT MAPPING
==================================================

The generated credential export must correspond exactly to the users successfully reset.

For example:

user A → generated password A
user B → generated password B

Never generate credentials first and then perform a separate unrelated reset.

The password/hash update and credential-artifact generation need a carefully designed relationship so we never accidentally give the wrong password to the wrong user.

Think carefully about failure handling.

If artifact generation fails, the corresponding user's password must not be changed without a recoverable credential record.

If a database update succeeds but credential persistence fails, the operation must STOP safely and report the affected user without exposing the password.

Do not pretend the operation is successful if the credential mapping cannot be guaranteed.
