STAGE 2 — RESET FLOW HARDENING AND CONTROLLED TEST PREPARATION

Stage 1 is complete.

DO NOT perform the mass user password reset.

DO NOT modify existing production user passwords.

DO NOT set passwordResetRequired=true for existing production users.

DO NOT increment authVersion for existing production users.

DO NOT deploy the mass-reset operation.

DO NOT expose passwords, password hashes, reset tokens, private keys, API keys, or other secrets.

We now need to prepare and verify the reset flow before production cutover.

==================================================
1. REVIEW STAGE 1 IMPLEMENTATION
==================================================

Review the implementation from Stage 1 for correctness.

Pay particular attention to:

- authVersion handling
- passwordResetRequired middleware behavior
- legacy JWT behavior while authVersion=0
- password change behavior
- admin-initiated user password reset behavior
- reset-token hashing
- reset-token expiration
- atomic token consumption
- rate limiting
- generic forgot-password responses
- logging

Do not redesign working components unnecessarily.

==================================================
2. DELIVERY ADAPTER
==================================================

Review:

password-reset-delivery.service.ts

The production adapter must FAIL CLOSED if no approved delivery provider is configured.

Do NOT add a fake production email provider.

Do NOT hard-code SMTP credentials.

Do NOT hard-code API keys.

Do NOT put credentials in source code.

Do NOT print reset tokens in production logs.

If a development/test adapter exists or is needed, ensure it is clearly isolated from production and cannot accidentally become the production delivery mechanism.

==================================================
3. TRUSTED RESET DOMAIN
==================================================

Verify exactly how reset URLs are constructed.

The reset URL must use the application's intended trusted production domain.

Do not allow a user-controlled Host header or arbitrary request origin to determine the reset URL.

Do not accept arbitrary redirect destinations.

Document the exact production reset URL format without exposing any secret token.

==================================================
4. CONTROLLED TEST ACCOUNT
==================================================

Create an automated/integration test fixture for ONE non-admin test user.

Do not modify a real production user.

Test this complete lifecycle:

A. User initially has:
   passwordResetRequired=false
   authVersion=N

B. Issue a JWT.

C. Increment authVersion.

D. Confirm the old JWT is rejected.

E. Set passwordResetRequired=true.

F. Confirm normal authenticated routes are blocked.

G. Request forgot-password.

H. Generate a reset token through the test delivery adapter ONLY.

I. Confirm only the token hash is persisted.

J. Confirm raw token is not logged.

K. Use the reset token.

L. Confirm token is consumed exactly once.

M. Confirm passwordResetRequired=false.

N. Confirm authVersion increments again.

O. Confirm the new password works.

P. Confirm the old password fails.

Q. Confirm the new JWT works.

R. Confirm the previous JWT remains invalid.

==================================================

- wallet balance
- locked withdrawal balance
- investments
- ROI
- deposits

Confirm password reset modifies NONE of those values.

6. ADMIN ISOLATION
==================================================

==================================================
7. STATUS BEHAVIOR
==================================================

The Stage 1 audit identified an existing issue:

INACTIVE users are not explicitly rejected by the user login service.

Do NOT silently change this behavior as part of the credential-reset implementation.

Instead:

- identify exactly how ACTIVE, INACTIVE, BLOCKED and SUSPENDED users behave after Stage 1
- document it
- add tests preserving current behavior
- flag it separately for a later decision

The mass reset must preserve all existing user statuses.
