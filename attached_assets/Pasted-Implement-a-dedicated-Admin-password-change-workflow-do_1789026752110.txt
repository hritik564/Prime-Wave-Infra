Implement a dedicated Admin password-change workflow — do not execute the password change yet

We need a secure way for the existing Super Admin admin@primewave.io to change their own Admin password.

Implement a dedicated authenticated endpoint for the currently logged-in Admin to change their own password.

Requirements:

Endpoint must operate on the Admin record, not User.
Only an authenticated Admin may change their own password.
The request must identify the current authenticated Admin from the verified JWT/session, not accept an arbitrary admin ID/email supplied by the client.
Require the current password before allowing the change.
Require a new password meeting the application's appropriate password-strength requirements.
Hash the new password using the same secure password-hashing mechanism already used by Admin login.
Update Admin.passwordHash.
Ensure Prisma updates Admin.updatedAt.
This updatedAt change must invalidate existing Admin JWTs under the session-invalidation mechanism already implemented.
Do not expose password hashes, current-password validation details, or secrets in responses/logs.
Return a generic success response.
Do not allow this endpoint to modify another Admin's password.
Do not reuse /api/auth/change-password, because that targets User.
Do not use /api/admin/users/:id/reset-password, because that targets User.
Do not use ADMIN_RESET_PASSWORD, because it affects all Admin accounts.

Add appropriate backend tests covering:

Successful own-admin password change.
Incorrect current password rejected.
Weak/invalid new password rejected.
Unauthenticated request rejected.
Existing Admin JWT becomes invalid after the password change because updatedAt changes.
Verify the endpoint cannot target another Admin account.

Add a minimal Admin Settings UI for the logged-in Admin to use this workflow if the existing Admin settings page is appropriate.

Important: Do NOT actually change any production password.
Do NOT modify any Admin account data.
Do NOT publish/redeploy.
Do NOT change roles, permissions, deposits, withdrawals, wallets, or financial data.

Run the relevant typechecks and tests and report exactly what was implemented.
