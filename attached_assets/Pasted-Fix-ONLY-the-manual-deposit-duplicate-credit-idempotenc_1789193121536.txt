OBJECTIVE

Make the existing manual-deposit operation safe against accidental duplicate execution caused by:

- double-clicks
- browser retries
- network retries
- repeated form submissions
- repeated API requests for the same intended manual credit

The current implementation generates a new MANUAL-UUID for every request, which means the same manual deposit can potentially be credited more than once.

REQUIRED BEHAVIOR

1. Add a proper idempotency mechanism to the manual deposit operation.

2. The client should generate/send an idempotency key for each intentional manual-deposit submission.

3. Retrying the SAME intentional submission must reuse the SAME idempotency key.

4. A repeated request with the same idempotency key must NOT:
   - create another deposit
   - credit the wallet again
   - create another successful wallet transaction
   - create another financial ledger entry
   - generate another manual deposit reference

5. Instead, the API should return the result of the original successful operation, or an equivalent safe idempotent response.

6. A NEW intentional manual deposit must use a NEW idempotency key and must continue to work normally.

7. Idempotency must be enforced SERVER-SIDE. Do not rely only on disabling the frontend submit button.

8. The idempotency record/check must be atomic and concurrency-safe so that two simultaneous requests carrying the same key cannot both perform the credit.

9. The idempotency key must be scoped appropriately to prevent one staff/admin account from accidentally or maliciously reusing another operator's key.

10. Do not use the amount alone, target user alone, reason alone, or timestamp alone as the duplicate-detection key. Different legitimate manual deposits can have the same values.

11. Preserve all existing authorization rules exactly as they currently work:
    - SUPER_ADMIN: existing behavior unchanged
    - FINANCE_ADMIN: existing behavior unchanged
    - STAFF_OPERATIONS: may credit ONLY depositWallet
    - STAFF_OPERATIONS must continue receiving 403 for incomeWallet and withdrawalWallet
    - Other unauthorized roles remain denied

12. Preserve all existing audit logging. The idempotency protection must not bypass or replace the existing audit record.

13. Preserve the existing financial transaction/DB transaction semantics. The wallet credit and its associated records must remain atomic.

14. If the request fails validation before the financial operation begins, do not permanently consume the idempotency key in a way that prevents the operator from correcting the request and retrying.

15. If the actual financial operation succeeds, the idempotency state must be committed together with the financial operation so there cannot be a successful credit without a corresponding idempotency record.

16. If the operation fails/rolls back, the same idempotency key should be safely retryable.

IMPORTANT DESIGN REQUIREMENT

First inspect the existing schema and manual-deposit implementation and choose the smallest robust implementation that fits the project's current architecture.

Prefer a database-backed unique constraint/index and transaction-safe implementation rather than an in-memory Map/cache.

If a Prisma schema/migration change is required, create the proper Prisma migration file. Do NOT apply the migration to production.

The implementation must work correctly across multiple API instances/processes.

API

Determine the correct existing manual-deposit endpoint(s) and make the idempotency protection cover every endpoint that can actually perform the same manual financial credit operation.

Do NOT blindly add duplicate logic to unrelated wallet-adjustment or withdrawal endpoints.

If there are multiple manual-credit routes that ultimately perform the same financial operation, make sure both are protected consistently.

ERROR/RETRY SEMANTICS

Use safe, deterministic behavior for repeated keys.

For example:

- First request succeeds → subsequent identical request with same key returns the original result without another credit.
- First request is still processing → concurrent/repeated request must not execute another credit.
- First request rolls back/fails → retry with same key remains possible.
- Same key reused for a materially different request payload → reject it rather than silently performing a different financial operation.

Store enough request identity/fingerprint information to detect key reuse with different parameters.

SECURITY

- Never store passwords, secrets, or sensitive authentication material in the idempotency record.
- Do not log sensitive information unnecessarily.
- Keep existing authentication and role checks.
- Keep existing audit logging.
- Do not allow idempotency to become a way to bypass authorization.
