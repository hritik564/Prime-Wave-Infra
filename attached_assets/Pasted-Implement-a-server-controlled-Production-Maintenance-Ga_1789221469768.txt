Implement a server-controlled Production Maintenance Gate for PrimeWave.

IMPORTANT:
This is an intentional, reversible operational access gate.

Do NOT simulate corrupted infrastructure, fabricate failures, damage data, create fake crash logs, or intentionally make the application appear accidentally broken.

The purpose of this feature is to allow the public PrimeWave website and normal Admin login to be temporarily unavailable while keeping the underlying API/database infrastructure operational.

I will control the maintenance state exclusively through the Replit Production environment.

Do NOT publish or deploy this implementation automatically.

==================================================
1. CONTROL VARIABLE
==================================================

Use this Production environment variable:

MAINTENANCE_MODE=false

Behavior:

- MAINTENANCE_MODE unset → normal operation
- MAINTENANCE_MODE=false → normal operation
- MAINTENANCE_MODE=true → maintenance gate active

Only the explicit string:

true

should enable the gate.

Do NOT create:

- Admin-panel maintenance toggle
- Admin Settings maintenance option
- Database maintenance setting
- Admin API endpoint for changing maintenance mode
- Frontend maintenance toggle
- User-accessible maintenance configuration
- Maintenance password
- Secret bypass token
- Hard-coded bypass mechanism

The only intended control is changing the Production environment variable through Replit and then performing the normal production restart/publish process.

Do NOT modify the Production environment variable during this implementation.

==================================================
2. PUBLIC WEBSITE BEHAVIOR
==================================================

When:

MAINTENANCE_MODE=true

all normal public/unauthenticated PrimeWave website access must return:

HTTP 503 Service Unavailable

The user should see a minimal PrimeWave-branded page.

The exact visible message must be:

Service Unavailable · 503

Please try again later.

Do not add additional explanations.

Do not display:

- "maintenance"
- "database error"
- "server error"
- "critical failure"
- "system failure"
- troubleshooting instructions
- estimated recovery time
- infrastructure information
- deployment information

- stack traces
- environment variables
- RPC URLs
- wallet information
- database information

Use the existing PrimeWave visual design language.

The page should look clean, intentional, and professional.

Do not make it look like a browser crash or corrupted application.

The HTTP response itself must genuinely be:

503 Service Unavailable

Do NOT use HTTP 500.

If compatible with the existing architecture, include:

Retry-After: 3600

==================================================
3. ADMIN LOGIN MUST ALSO BE BLOCKED
==================================================

When:

MAINTENANCE_MODE=true

the normal PrimeWave Admin login path must also be unavailable.

Specifically:

- The normal Admin login page must not allow login.
- The Admin authentication/login API endpoint must reject new login attempts.
- New unauthenticated Admin users must not be able to establish an Admin session through the normal login flow.
- The login response should use the same 503 maintenance response where technically appropriate.
- Do not reveal whether the supplied email exists.
- Do not reveal whether the password is correct.
- Do not reveal Admin roles.
- Do not expose authentication implementation details.

The user-facing response should remain consistent with:

Service Unavailable · 503

Please try again later.

IMPORTANT:

Do NOT:

- delete Admin accounts
- disable Admin accounts
- change Admin passwords
- change Admin roles
- invalidate JWTs
- delete sessions
- modify authentication records
- modify authorization rules

The gate must only prevent new normal Admin authentication while MAINTENANCE_MODE=true.
