SPRINT 28H — GENESIS GENERATOR REARCHITECTURE & PERFORMANCE FIX

IMPORTANT

This sprint is NOT about making the current implementation "a little faster."

This sprint is about designing the correct architecture for large-scale genesis generation.

The production runtime placement engine and the genesis generator have different responsibilities and should not be forced to share identical execution paths if that introduces unnecessary overhead.

==========================================================
OBJECTIVE
==========================================================

Reduce production genesis generation time from hours to minutes while preserving:

• Identical binary tree
• Identical referral structure
• Identical usernames
• Identical wallets
• Identical funding
• Identical final database state

The final generated network must be byte-for-byte equivalent from a business perspective.

==========================================================
ARCHITECTURAL GOAL
==========================================================

The genesis generator is a one-time infrastructure tool.

The runtime placement engine is a permanent production component.

Avoid adding generator-only parameters such as:

forcedPlacementTargetId

skipCacheUpdate

or other generator-specific flags into production runtime APIs unless there is absolutely no cleaner solution.

First evaluate whether the generator can use its own optimized placement path.
