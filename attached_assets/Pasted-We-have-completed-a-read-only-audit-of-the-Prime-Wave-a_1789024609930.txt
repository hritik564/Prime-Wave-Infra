DEPOSIT POLICY

The intended production policy is:

Normal users:
Automatic Deposit → blockchain transaction → automatic verification → automatic wallet credit.

Staff:
Can monitor automatic deposits but cannot manually approve or credit deposits.

Super Admin:
Can perform exceptional manual credits/manual deposit operations and can change the company deposit wallet.

AUTHORIZATION HARDENING

Fix these specific gaps identified by the audit:

1. SYSTEM SETTINGS
The current PATCH /api/admin/settings/:key allows any authenticated admin to modify arbitrary settings.

Change this so only SUPER_ADMIN can modify platform/system settings.

Staff must receive the normal authorization/forbidden response.

2. MATCHING/ORBIT TRIGGERS
The current manual matching and orbit trigger endpoints are available to any authenticated admin.

Restrict these triggers to SUPER_ADMIN only.

3. POWER BUSINESS
Any authenticated admin can currently read Power Business financial data.

Restrict sensitive Power Business financial/member-level reads to SUPER_ADMIN unless there is a clearly necessary read-only Staff operation. Do not expose financial data to Staff by default.

Power Business add/remove operations must remain SUPER_ADMIN-only for the new Staff model.

4. DEPOSIT VERIFICATION DUPLICATE ROUTE
The audit identified duplicate mounting of the deposit-verification router, where one route definition uses weaker any-admin authorization.

Remove the weaker duplicate path or otherwise ensure every deposit-verification endpoint has one consistent authorization boundary.

Staff must never be able to reach manual approval/rejection/financial mutations through an alternate route.

5. JWT ADMIN AUTHORIZATION
The current middleware does not reload the admin database record for every request, meaning:
- role changes remain effective until the JWT expires
- deactivation does not immediately invalidate an existing admin JWT

Improve admin session authorization so that disabling an admin account or changing its role prevents that account from continuing to perform protected operations with an already-issued token.

Use a safe and efficient mechanism appropriate to the existing architecture. Do not unnecessarily add a database query to every request if a better existing session/token invalidation mechanism can be implemented.

This is particularly important because we will shortly disable two existing admin accounts and rotate the Super Admin credentials.

6. FRONTEND CONTROL CENTER
The current Control Center navigation renders almost all sections for every authenticated admin even when the backend rejects them.

Implement proper role/permission-based navigation for Staff.

Staff should see only:

OVERVIEW
- Dashboard

MANAGEMENT
- Members
- Investments
- Deposits
- Auto Deposits
- Withdrawals
- W. Queue
- W. Ops Health
- Wallets

Everything else should be hidden from Staff.

Also remove/hide mutation buttons that Staff cannot execute.

Do NOT treat frontend hiding as security. Backend authorization remains mandatory.

7. ADMIN ROUTE GUARDS
The frontend currently allows any admin to navigate directly to /admin/... pages because RequireAdmin only checks user.type === admin.

Add appropriate role/permission checks so Staff cannot directly access restricted Control Center pages.

Unknown admin paths should not expose privileged page shells.

8. DEV-TOOLS FRONTEND
Ensure /dev-tools is protected by appropriate admin authorization in all environments, not merely hidden/redirected based on build mode.

No unauthenticated or Staff user should receive privileged developer-tool UI.
