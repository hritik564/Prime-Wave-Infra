SPRINT 27B — DEPOSIT VERIFICATION HARDENING & RECOVERY

OBJECTIVE

This sprint completes the Deposit Verification subsystem for production.

The goal is:

1. Eliminate the stale recipient snapshot issue permanently.
2. Prevent invalid wallet configuration from ever reaching production again.
3. Allow administrators to recover failed verifications safely.
4. Preserve financial integrity.
5. Preserve complete auditability.

IMPORTANT

Do NOT redesign the verification engine.

Do NOT duplicate any wallet credit logic.

Do NOT modify financial calculations.

Reuse existing production code wherever possible.

==========================================================
PART 1 — KEEP SNAPSHOT ARCHITECTURE
==========================================================

The snapshot design is correct.

DepositVerification.recipientAddress must remain an immutable snapshot of the expected wallet at the moment the user submitted the transaction.

The worker MUST continue verifying against this snapshot.

Do NOT change the worker to query company_wallets live during verification.

Reason:

Changing wallets after submission must NOT invalidate legitimate historical deposits.

==========================================================

==========================================================
PART 3 — CONFIGURATION SAFETY
==========================================================

During submitVerification()

before creating DepositVerification

validate:

• active company wallet exists
• wallet is active
• wallet format is valid
• wallet is NOT a placeholder
• only one active wallet exists for that network

If validation fails

reject submission

Return HTTP 503

Example

"Deposit verification is temporarily unavailable due to server configuration."

Never create an invalid verification record.

==========================================================

BEP20

ERC20

TRC20

SOL

✓ wallet exists

✓ exactly one active wallet

✓ valid address format

FAIL SERVER STARTUP
