STAGE 5N — BUILD COMMON TEMPORARY PASSWORD OPERATION
IMPLEMENTATION + TESTING ONLY — NO PRODUCTION EXECUTION

We currently have an existing production bulk password reset run actively processing:

- totalEligible: 6,640
- status: RUNNING
- processedCount checkpoint is currently behind the actual authentication-state count
- failedCount: 0

The existing run MUST be allowed to finish naturally.

We now need a NEW, separate Super Admin-only operation that can set ONE common temporary password for all normal users.

IMPORTANT:
THIS TASK IS IMPLEMENTATION AND TESTING ONLY.

DO NOT:
- execute the new operation against production
- call any production password-changing endpoint
- modify production users
- modify production admins
- modify production financial/business data
- modify the existing RUNNING bulk reset
- cancel, resume, retry, or fail the existing run
- download/read the existing random-password credential artifact
- generate the common password automatically
- store any plaintext password
- expose passwords, hashes, JWTs, cookies, private keys, or secrets

==================================================
1. REQUIREMENT
==================================================

Build a new operation called:

COMMON TEMPORARY PASSWORD RESET

Purpose:

A Super Admin enters ONE temporary password in the Admin UI.

That same password is applied to every normal User account.

Admins are ALWAYS excluded.

The operation must support the existing User population regardless of status:

- ACTIVE
- INACTIVE
- BLOCKED
- SUSPENDED

Do not alter user status.

==================================================
2. SECURITY REQUIREMENTS
==================================================

The plaintext password must NEVER be:

- stored in PostgreSQL
- stored in logs
- stored in admin_logs
- stored in Redis/cache
- included in API responses
- included in error messages
- included in artifacts
- included in URLs
- included in analytics
- printed to console

The backend should receive the password only for the duration necessary to calculate its bcrypt hash.

Use the application's existing bcryptjs configuration and security conventions.

Do not invent a weaker hashing configuration.

Never return the password or hash to the frontend.

==================================================
3. SUPER ADMIN ONLY
==================================================

Create a dedicated endpoint, for example:

POST /api/admin/security/common-password-reset/preview

POST /api/admin/security/common-password-reset/execute

Both must require:

requireAdminRoles("SUPER_ADMIN")

Do not allow any other admin role.

Do not alter existing admin authorization middleware.

==================================================
4. PREVIEW
==================================================

The preview endpoint must be READ-ONLY.

It should report:

- total normal users
- ACTIVE
- INACTIVE
- BLOCKED
- SUSPENDED
- total admins detected
- admins excluded
- current users with passwordResetRequired=true
- current users with authVersion != 0
- whether another credential-reset operation is active
- whether the operation is currently eligible to execute

The preview MUST NOT receive or require the plaintext password.

Do not create a run record merely for preview.

==================================================
5. ACTIVE-RUN SAFETY LOCK
==================================================

This is CRITICAL.

The new common-password execute operation MUST refuse execution if ANY existing credential reset operation is active.

Specifically, while the current random bulk reset has:

status = RUNNING

the common-password execute endpoint must return a clear conflict response.

For example:

HTTP 409

code:
BULK_RESET_ALREADY_RUNNING

message:
"Another bulk credential reset operation is currently running."

Do not bypass this check.

The check must occur server-side.

Do not rely only on frontend button disabling.

==================================================
6. COMMON PASSWORD EXECUTION
==================================================

Execution must require:

- authenticated SUPER_ADMIN
- exact expected user count
- explicit confirmation phrase
- plaintext password supplied through a secure password field
- password confirmation field matching exactly
- password strength validation
- no active credential reset run

Suggested confirmation phrase:

SET COMMON TEMPORARY PASSWORD FOR ALL NORMAL USERS

Do not execute unless every condition passes.

==================================================
7. PASSWORD PROCESSING
==================================================

The operation should:

1. Receive the plaintext password.
2. Validate it.
3. Hash it using the existing bcryptjs security configuration.
4. Never persist the plaintext.
5. Apply the resulting password hash to normal User records in controlled batches.
6. Set:

passwordResetRequired = true

7. Increment authVersion for each affected user.
8. Set passwordChangedAt.
9. Preserve all other User fields.
10. Preserve user status.
11. Preserve financial/business relationships.

Admins must not be modified.

==================================================
8. IMPORTANT: HASH REUSE
==================================================

Because the same password is intentionally being used for this internal operation, do NOT generate one random password per user.

However, inspect the application's bcrypt implementation and determine whether using the same bcrypt hash for all users is acceptable under the current security model.

If the existing security architecture requires unique bcrypt salts per user, then hash the SAME plaintext password separately for each user using bcrypt so each resulting hash has its own salt.

The plaintext common password remains identical.

Do not weaken the password hashing security merely to make the operation faster.

==================================================
9. BATCHING / LONG-RUN SAFETY
==================================================

The previous bulk reset demonstrated that an HTTP request can exceed the Replit request timeout.

DO NOT implement the new operation as one long synchronous HTTP request.

Design the common-password operation as a resumable server-side job/control-plane operation.

The HTTP request should:

- validate authorization
- validate confirmation
- validate password
- establish a run
- securely establish the operation state
- return a run ID / accepted response

The actual processing should happen through the application's existing safe job/background mechanism if one exists.

Inspect the repository for existing job infrastructure before creating new infrastructure.

The job must checkpoint progress.

Suggested batch size: 250, but use repository conventions if a safer existing batch mechanism exists.

==================================================
11. NO PLAINTEXT PASSWORD IN RUN RECORD
==================================================

The run record must NEVER contain:

- plaintext password
- password confirmation
- password-derived reversible value

Do not attempt to recover the password later from the run.

The operation should only need the plaintext during execution.

If background processing requires persistence across processes, design the mechanism so the plaintext is not persisted. For example, use an ephemeral in-memory execution context only if the existing Replit architecture safely supports it.

If safe background persistence of the plaintext cannot be guaranteed, STOP and report the architectural limitation rather than storing the password.
