Implement a secure first-login password-change flow for users where passwordResetRequired=true.

Current problem:

POST /api/auth/login returns 403 PASSWORD_RESET_REQUIRED before bcrypt verification.
POST /api/auth/change-password uses normal requireAuth, which also rejects passwordResetRequired=true.
Therefore flagged users cannot authenticate or change their temporary password.

Implement the safest design:

During normal user login, perform identifier lookup and account checks, then verify the supplied password with the existing bcrypt mechanism.
If the password is correct AND passwordResetRequired=true, do NOT issue a normal authenticated session/JWT.
Instead issue a short-lived, purpose-specific password-reset authentication mechanism that can ONLY authorize the password-change operation. It must not grant normal API access, withdrawals, transfers, profile access, or other authenticated functionality.
The restricted reset session/token must be cryptographically secure, short-lived, single-purpose, and invalidated after successful password change.
POST /api/auth/change-password must explicitly accept this restricted reset authentication state for users whose passwordResetRequired=true.
After successful password change:
verify the current/temporary password as appropriate for the established flow
hash the new password using the existing bcrypt configuration
set passwordResetRequired=false
increment authVersion
update passwordChangedAt
invalidate the restricted reset session/token
issue the normal authenticated session/JWT only after the new password is successfully established
A restricted reset token must never be accepted by normal requireAuth routes.

Do not change the behavior of users whose passwordResetRequired=false.
