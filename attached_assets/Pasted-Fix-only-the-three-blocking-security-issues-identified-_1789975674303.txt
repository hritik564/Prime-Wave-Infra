1. Eliminate normal-JWT access to password change

POST /api/auth/change-password must require the restricted password-reset authentication state when passwordResetRequired=true.

A normal user JWT must NOT be sufficient.

Require all relevant restricted-token invariants:

type=password_reset
purpose=password_change
correct user identity
matching authVersion
passwordResetRequired=true

Preserve normal password-change behavior for users who are not in the forced-reset state if that route currently supports it, but do not weaken the forced-reset security boundary.

2. Make the restricted reset authentication truly single-use under concurrency

Eliminate the race where two simultaneous password-change requests can validate the same restricted authentication before either request updates the user.

Use an atomic/optimistic condition so that only one request can successfully consume the reset authentication.

The successful operation must atomically establish:

new password hash
passwordResetRequired=false
authVersion increment
passwordChangedAt
consumption/invalidation of the restricted reset authentication

A concurrent second request using the same restricted authentication must fail safely and must not change the password or issue a normal session.

Do not rely only on a separate preliminary token validation followed by an unconditional user.update().

3. Do not return the restricted reset token in the JSON response

The current login response returns the restricted reset token in data.resetToken. Remove this.

Use a secure short-lived delivery mechanism that satisfies these requirements:

not included in JSON response
not placed in URL/query parameters
not stored in localStorage/sessionStorage
not logged
purpose-specific
expires after 10 minutes
protected against CSRF if cookies are used
cannot be used as a normal user authentication token
invalidated after successful password change

Prefer an HttpOnly, Secure, SameSite-appropriate, short-lived cookie or an equivalent server-side mechanism consistent with the existing authentication architecture.

If using a cookie, ensure the password-change endpoint validates the appropriate CSRF protection and that the cookie cannot authenticate normal protected API routes.
