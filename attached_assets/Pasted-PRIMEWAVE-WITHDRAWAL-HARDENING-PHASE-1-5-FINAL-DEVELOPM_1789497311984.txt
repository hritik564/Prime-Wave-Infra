1. REAL POSTGRESQL CONCURRENCY TEST
==================================================

Create a genuine PostgreSQL integration test for the withdrawal claim mechanism.

Do NOT mock the database transaction boundary.

Use the actual development PostgreSQL database/schema.

The test must create a realistic PENDING withdrawal and then launch at least two concurrent claim attempts representing two independent worker instances.

The test must prove:

- Both workers can attempt to claim simultaneously.
- Exactly ONE worker obtains the withdrawal claim.
- The other worker receives no claim.
- The withdrawal cannot be claimed twice.
- The winning worker owns the claim.
- The claim token is unique.
- The claim expiration is recorded correctly.
- The database state after the race is internally consistent.
- No duplicate processing state is created.

Use actual PostgreSQL concurrency.

Do not replace the test with:

- sequential calls
- JavaScript mutexes
- fake transactions
- mocked Prisma transactions
- mocked `FOR UPDATE`
- mocked claim results

The test should exercise the actual database locking/transaction behavior.

If the existing test infrastructure makes this difficult, create the smallest dedicated integration-test harness necessary.

Do not weaken production code merely to make the test pass.

==================================================
2. REAL DEVELOPMENT-DATABASE ACCOUNTING TEST
==================================================

Create a real PostgreSQL integration test covering successful withdrawal completion.

Use actual development database rows.

Create a realistic test fixture containing:

- User
- Initial available balance
- Initial locked withdrawal balance
- Withdrawal request
- Appropriate wallet transaction/accounting state

Then execute the real completion/recovery service.

Verify atomically that:

1. Withdrawal becomes COMPLETED.
2. Completion metadata is stored correctly.
3. Locked withdrawal balance decreases exactly once.
4. The amount released/decremented is correct.
5. The wallet ledger contains exactly one successful withdrawal transaction.
6. `withdrawalRequestId` uniqueness prevents duplicate ledger entries.
7. Re-running the completion/recovery operation does not:
   - decrement locked balance again
   - create another wallet transaction
   - duplicate any financial side effect
8. A concurrent duplicate completion attempt cannot create duplicate financial effects.

The test must use the actual development PostgreSQL database.

Do not mock Prisma transactions for this integration test.

3. RECOVERY / BROADCAST_UNKNOWN INTEGRATION TEST
==================================================

Add a development-database integration test for the ambiguous broadcast scenario.

Create a realistic withdrawal that reaches the relevant state.

Verify:

- A timeout/network-level broadcast failure does NOT automatically refund the user.
- The withdrawal enters `BROADCAST_UNKNOWN` or the implemented equivalent.
- Locked funds remain protected.
- No successful wallet ledger entry is created.
- No duplicate refund is created.
- Reconciliation can safely process the state later.
- Re-running reconciliation remains idempotent.

Do not perform any real blockchain broadcast.

Mock only the blockchain/RPC boundary, not the database boundary.
