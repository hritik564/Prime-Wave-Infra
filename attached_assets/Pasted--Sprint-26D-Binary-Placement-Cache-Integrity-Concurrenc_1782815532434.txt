# Sprint 26D — Binary Placement Cache Integrity & Concurrency Hardening

## Objective

Fix the binary placement cache architecture so it remains permanently consistent with the binary tree, even after millions of registrations, while preserving existing placement rules and making registration safe under concurrent requests.

This sprint is **not** a feature sprint. It is an infrastructure reliability sprint.

**This is production-critical.**

---

# Root Cause

Current implementation updates:

- placement target cache
- immediate sponsor cache

and stops.

This allows ancestor caches (MASTERROOT, etc.) to become permanently stale as registrations occur deeper in the tree.

Additionally, placement currently executes under READ COMMITTED without any row-level locking, allowing concurrent registrations to compete for the same placement slot.

Both issues must be fixed.

---

# Requirements

## Part 1 — Rewrite Cache Propagation

Replace the existing sponsor-only cache update logic.

After a successful placement:

1. Place user into the binary tree.
2. Update the placement target cache.
3. Walk upward through **every ancestor** using `binaryParentId`.
4. Update the appropriate cache pointer for **every ancestor**.
5. Commit the transaction.

Example:

MASTERROOT

↓

A

↓

B

↓

C

↓

D

↓

NEW

After NEW is inserted, update cache for:

- D
- C
- B
- A
- MASTERROOT

Every ancestor's LEFT or RIGHT deepest pointer must reference the newest deepest available node in that subtree.

Do **not** stop at the immediate sponsor.

---

## Part 2 — Automatic Cache Self-Healing

If the cached node fails validation:

### Current behaviour

Throw `CACHE_INCONSISTENCY`.

### New behaviour

1. Validate cached node.
2. If valid → continue normally.
3. If invalid:
   - Walk the actual binary tree.
   - Recalculate the correct deepest available node.
   - Repair the cache.
   - Continue registration automatically.

Only throw an error if the binary tree itself is structurally invalid.

Users should never see a cache inconsistency error caused only by stale cache data.

---

## Part 3 — Cache Rebuild Helper

Implement:

`rebuildPlacementCache(tx, sponsorId, side)`

The helper should:

- Walk only one subtree.
- Determine the correct deepest available node.
- Update the cache.
- Return the repaired node.

Complexity should remain **O(depth)**.

Do **not** rebuild the entire tree.

---

## Part 4 — Concurrency Hardening

Current implementation allows two concurrent registrations to claim the same placement target.

Fix this.

Before determining placement:

- Acquire a database row-level lock on the placement target (or an equivalent PostgreSQL locking mechanism).

Requirements:

- Only one transaction may claim a placement slot at a time.
- The second registration must wait until the first commits.
- After waiting, re-read the cache and continue normally.
- Duplicate placements must be impossible.

Do **not** use application-level mutexes.

Use PostgreSQL locking.

## Part 6 — Binary Integrity Audit Utility

Create a development-only verification utility.

For every user:

- Compute deepest LEFT node directly from the tree.
- Compare with cached LEFT pointer.
- Compute deepest RIGHT node directly from the tree.
- Compare with cached RIGHT pointer.

Generate a report showing:

- Users scanned
- Correct caches
- Repaired caches
- Remaining mismatches

This tool must be available only in development.

# Critical Architectural Requirement

Do **not** simply patch the existing cache logic.

Replace it with a cache maintenance strategy whose invariant is:

> For every node in the binary tree, `leftDeepestNodeId` and `rightDeepestNodeId` must always equal the deepest currently available placement node in that respective subtree.

If a cache ever diverges from the tree, it must be repaired automatically during placement rather than causing registration to fail.

The final implementation must leave the binary placement engine resilient to:

- Deep trees
- Stale caches
- Concurrent registrations

without changing any MLM business rules.
