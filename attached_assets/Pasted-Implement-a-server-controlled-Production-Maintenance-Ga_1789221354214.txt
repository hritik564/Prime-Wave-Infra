Implement a server-controlled Production Maintenance Gate for PrimeWave.

IMPORTANT:
This is an intentional, reversible operational maintenance gate.

Do NOT simulate a corrupted system, fabricate failures, create fake logs, damage data, or conceal what the application is doing.

The maintenance control must NOT exist anywhere in the PrimeWave Admin UI.

I will control it exclusively through the Replit Production environment.

==================================================
1. CONTROL VARIABLE
==================================================

Use this production environment variable:

MAINTENANCE_MODE=false

Behavior:

- MAINTENANCE_MODE unset → normal operation
- MAINTENANCE_MODE=false → normal operation
- MAINTENANCE_MODE=true → maintenance mode

Only the explicit string "true" should enable maintenance mode.

Do NOT create:

- Admin panel toggle
- Admin Settings option
- Database setting
- Admin API endpoint
- Frontend toggle
- User-accessible configuration
- Secret bypass token

The only control should be the Replit Production environment variable followed by the normal production restart/publish process.

Do NOT modify the Production environment variable during this task.

==================================================
2. PUBLIC WEBSITE
==================================================

When MAINTENANCE_MODE=true:

Public/unauthenticated website access must return:

HTTP 503 Service Unavailable

Display a professional PrimeWave maintenance page.

Suggested text:

"PrimeWave is temporarily unavailable"

"Service is currently unavailable while maintenance is being performed. Please try again later."

Use the existing PrimeWave visual design language.

Do not expose:

- stack traces
- database information
- infrastructure details
- server paths
- environment variables
- RPC URLs
- wallet addresses
- private configuration
- deployment information
- internal service names

If compatible with the architecture, include:

Retry-After: 3600

The response must genuinely use HTTP 503.

Do not return HTTP 500.

==================================================
3. ADMIN LOGIN MUST ALSO BE BLOCKED
==================================================

When MAINTENANCE_MODE=true:

The normal Admin login experience must also be unavailable.

Specifically:

- Admin login page must not be usable.
- Admin login API/authentication route must reject new Admin login attempts.
- Existing unauthenticated users must not be able to authenticate into the Admin panel through the normal login flow.
- The response should remain a clean HTTP 503 maintenance response.
- Do not expose whether a supplied email/password combination is valid.
- Do not reveal account existence.
- Do not reveal Admin roles.
- Do not expose authentication implementation details.

The goal is that the normal Admin login path is unavailable while maintenance mode is active.

IMPORTANT:

Do NOT delete, disable, modify, or invalidate Admin accounts.

Do NOT change passwords.

Do NOT modify JWT/session records.

Do NOT modify Admin roles.

Do NOT modify authorization rules.

This is only a temporary access gate controlled by MAINTENANCE_MODE.

==================================================
4. EXISTING ADMIN SESSIONS
==================================================

Because Admin login is intentionally unavailable during maintenance mode, determine how the existing architecture handles already-authenticated Admin sessions.

Prefer the safest behavior that does NOT modify authentication state or invalidate sessions.

However, if allowing an existing Admin session to continue would create an unintended way to bypass the maintenance gate, ensure the normal Admin UI cannot be accessed through the public website while maintenance mode is active.

Do NOT invent a new authentication bypass.

Do NOT create a hard-coded Admin credential.

Do NOT create a maintenance password.

Do NOT expose an alternate login mechanism.

I will handle any alternate administrative access mechanism separately later.

==================================================
5. API BEHAVIOR
==================================================

Do NOT shut down the entire API.

The database and API infrastructure must remain operational.

Do not globally return 503 from all API routes.

However, the normal Admin authentication/login endpoint must be blocked while maintenance mode is active as described above.

Do not interfere with unrelated backend services.

Do not modify:

- deposit verification
- automatic deposits
- company wallet management
- QR management

- Power Business
- withdrawal processing

==================================================

Inspect the existing application and deployment architecture.

Do not break any endpoint required by Replit or the production runtime to determine whether the service is alive.

If the project has health/readiness endpoints used by deployment infrastructure, preserve their existing behavior unless there is a compelling architectural reason not to.

The goal is:

Public application unavailable → 503

while:

Underlying application process/database → operational

==================================================

Do not rely solely on:

- React state
- frontend route guards
- JavaScript redirects
- hidden UI elements

A user must not be able to bypass maintenance mode simply by directly requesting the public URL.

Do not expose MAINTENANCE_MODE to the browser unless absolutely necessary.

Do not create a client-side switch.

Do not add a maintenance secret.

Do not add a hard-coded bypass.

Do not alter existing role permissions.

==================================================

The normal application must automatically return to its existing behavior after the normal production restart/redeploy.

Do not require:

- database changes
- code changes
- Admin UI actions
- manual data repair

No application state should remain permanently changed after maintenance mode is disabled.
