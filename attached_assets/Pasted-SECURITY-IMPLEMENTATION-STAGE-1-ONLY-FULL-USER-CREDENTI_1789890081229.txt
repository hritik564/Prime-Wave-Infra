==================================================
1. USER SCHEMA
==================================================

Add to the normal User model:

passwordResetRequired Boolean @default(false)
authVersion Int @default(0)

Optionally add:

passwordChangedAt DateTime?

Do NOT modify existing passwordHash values.

Do NOT modify user status values.

Do NOT modify wallet, investment, ROI, deposit, withdrawal, income, referral, BV, or other business fields.

Create a proper Prisma migration.

==================================================
2. RESET TOKEN MODEL
==================================================

Create a secure reset-token model/table.

Requirements:

- unique token record ID
- userId foreign key
- tokenHash
- createdAt
- expiresAt
- usedAt nullable
- optional request metadata if already supported by the architecture

NEVER store the raw reset token.

NEVER log the raw reset token.

NEVER log passwords.

The raw reset token may exist only transiently in the request/response flow and should be delivered through the intended trusted channel.

Add appropriate indexes and foreign keys.

Reset tokens must support atomic single-use consumption.

==================================================
3. JWT AUTH VERSION
==================================================

Modify normal USER JWT generation to include:

authVersion

Use the current user's authVersion at token issuance.

Modify normal user requireAuth middleware:

1. Verify JWT signature.
2. Verify expiration.
3. Load current user authentication state.
4. Compare JWT authVersion against database authVersion.
5. Reject stale tokens.
6. If passwordResetRequired=true, prevent access to normal authenticated routes.
7. Allow only the password-reset completion flow and any explicitly required unauthenticated/reset endpoints.

Do NOT alter Admin authentication behavior.

Admin JWT/session logic must remain exactly as currently implemented.

==================================================
4. AUTH VERSION INVALIDATION
==================================================

Create a safe mechanism so that incrementing:

users.authVersion

invalidates every previously issued JWT for that user.

Do not create a token blacklist.

Do not create a session table unless technically necessary.

The database authVersion is the source of truth.

==================================================
5. PASSWORD RESET ENDPOINTS
==================================================

Implement a real server-side password reset flow.

Required conceptual endpoints:

POST /api/auth/forgot-password
POST /api/auth/reset-password

Follow the project's existing API conventions.

FORGOT PASSWORD:

- accept email/username according to existing account model
- response must not reveal whether an account exists
- generate a cryptographically secure random reset token
- store only its hash
- set a short expiration
- invalidate/expire previous outstanding reset tokens for that user as appropriate
- rate-limit requests
- never log the raw token
- never log the password

RESET PASSWORD:

- accept reset token + new password
- validate token hash
- validate expiration
- validate unused status
- atomically consume the token
- hash the new password with existing bcrypt configuration
- set passwordResetRequired=false
- increment authVersion
- update passwordChangedAt if implemented
- issue a new normal user JWT only after successful completion

Concurrent requests must not allow the same reset token to succeed twice.

==================================================
6. FORCED RESET BEHAVIOR
==================================================

When passwordResetRequired=true:

- old password must not provide normal authenticated access
- old JWT must not provide normal authenticated access
- only the reset completion flow should be available
- after successful reset, normal access resumes

Do NOT yet set this flag on existing production users.

==================================================
7. PASSWORD POLICY
==================================================

Reuse the application's existing password validation policy if one exists.

If the existing policy is insufficient, implement a clear minimum policy appropriate for production.

Do not generate temporary passwords.

Do not use Math.random() for credential generation.

Use cryptographically secure randomness wherever secrets/tokens are generated.
